## چرا بازبینی مهندسی اهمیت دارد

Iran-OS یک قرارداد منفرد نیست. یک سیستم چندقراردادی است که در آن Kernel، پروتکل‌های اجرایی، صندوق ثروت ملی، رفاه شهروندی، دادگستری و بازیابی دارایی با هم integrate شده‌اند.

درستی معماری، ترتیب استقرار، سیم‌کشی اوراکل، طراحی state، پوشش رویداد و قابلیت نگهداری — همه این‌ها پیش از هر بحث امنیتی باید بررسی شوند.

اگر معماری نادرست طراحی شده باشد، امنیت آن اهمیتی ندارد.

---

## حوزه‌های نیازمند بازبینی

**۱. گراف وابستگی چندقراردادی**
آیا وابستگی‌های بین قراردادها منطقی، یک‌طرفه و قابل ردیابی هستند؟ آیا حلقه‌های وابستگی غیرضروری وجود دارد؟

**۲. وابستگی دایره‌ای Kernel / TriggerProtocol**
`IranOS_Kernel` آدرس `TriggerProtocol` را نیاز دارد و `TriggerProtocol` آدرس Kernel را. این وابستگی دایره‌ای در استقرار چگونه حل می‌شود؟ آیا ترتیب initialization مستند شده؟

**۳. ترتیب استقرار و فرض‌های Deployment Manifest**
آیا یک ترتیب استقرار مشخص و قابل تکرار تعریف شده؟ اگر یک قرارداد در میانه استقرار fail کند، سیستم در چه وضعیتی باقی می‌ماند؟

**۴. بازبینی قراردادهای اصلی**
لطفاً معماری و منطق تمام قراردادهای زیر بررسی شود:
- `contracts/kernel.sol` — هسته حکمرانی، لایه صفر
- `contracts/core/TriggerProtocol.sol` — لایه اجرا
- `contracts/core/ConstitutionGuard.sol` — دروازه‌بان قانون
- `contracts/monetary/SovereignWealthFund.sol` — صندوق ثروت سه‌لایه
- `contracts/monetary/PahlaviToken.so` — توکن ملی (توجه: پسوند `.so` به جای `.sol` — فایل Solidity است و توسط Hardhat و Foundry به‌صورت پیش‌فرض کامپایل نمی‌شود و نیاز به پیکربندی دستی دارد)
- `contracts/governance/Provincial.sol` — حکمرانی استانی
- `contracts/welfare/CitizenCard.sol` — کارت رفاه شهروندی
- `contracts/oracles/API3Oracle.sol` — اوراکل داده
- `contracts/justice/JurySelection.sol` — انتخاب هیئت منصفه با VRF
- `contracts/reclaim/AssetFreeze.sol` — پروتکل انجماد دارایی

**۵. مرزهای یکپارچه‌سازی API3 / Airnode**
آیا نقاط اتصال اوراکل به‌درستی تعریف شده‌اند؟ آیا قرارداد برای کار با Airnode RRP یا dAPI به‌درستی پیکربندی شده؟

**۶. Enumeration نوع داده اوراکل**
`API3Oracle` شش نوع داده (PRICE، PRODUCTION، GOVERNANCE، JUDICIAL، MILITARY، WELFARE) می‌پذیرد. آیا مرزهای enumeration بررسی می‌شوند؟ آیا ورودی خارج از محدوده رد می‌شود؟

**۷. پوشش رویداد برای سیستم‌های off-chain**
آیا رویدادهای کافی برای indexing، monitoring و نمایش در اپلیکیشن ملی emit می‌شوند؟ آیا رویدادی هست که باید باشد اما نیست؟

**۸. Storage Layout و state زائد**
آیا layout متغیرهای state کارآمد است؟ آیا متغیر یا mapping زائدی وجود دارد که هزینه gas را افزایش می‌دهد؟

**۹. ثابت‌های immutable و فرض‌های overflow**
`LIQUIDITY_CAP = 900_000_000_000 × 1e18` یک عدد بسیار بزرگ است. آیا در محاسبه‌های مرتبط (ضرب، تقسیم، مقایسه) احتمال overflow یا underflow وجود دارد؟ آیا SafeMath یا Solidity ^0.8 کافی است؟

**۱۰. قابلیت نگهداری بدون Proxy**
طبق طراحی، Kernel هیچ proxy upgrade pattern ندارد. اگر باگی غیرامنیتی در سایر قراردادها کشف شود، مسیر اصلاح چیست؟ آیا این مسیر مستند است؟

**۱۱. ذخیره‌سازی biometricToAddress در CitizenCard**
`mapping(bytes32 => address) public biometricToAddress` داده بیومتریک را on-chain ذخیره می‌کند. نگرانی اصلی storage یا gas نیست — EVM mapping اسپارس است. نگرانی واقعی این است: داده بیومتریک on-chain **عمومی و دائمی** است. اگر hash‌ها leak شوند، بازسازی شوند یا تابع hash در آینده ضعیف تشخیص داده شود، هویت ۸۰ میلیون شهروند برای همیشه در معرض خطر قرار می‌گیرد. آیا این رویکرد از نظر حریم خصوصی قابل دفاع است؟ آیا تابع hash انتخاب‌شده برای این مقیاس کافی است؟

**۱۲. منطق تخصیص ۳۰/۷۰ و bonus استانی در Provincial.sol**
فرمول درآمد: ۳۰٪ استانی، ۷۰٪ خزانه ملی. استان‌هایی با `productivityScore > 70` واجد شرایط bonus هستند. آیا منطق محاسبه درصد و معیار واجد شرایط بودن در تمام حالات ورودی به‌درستی عمل می‌کند؟

**۱۳. مسیر استقرار: hardhat.config.js در برابر Foundry**
`hardhat.config.js` در مخزن موجود است. Foundry نیز در stack ذکر شده. کدام ابزار برای استقرار واقعی استفاده خواهد شد؟ آیا هر دو مسیر تست شده‌اند؟

**۱۴. شبکه هدف، deployment script و وضعیت testnet**
این اولین سوال هر blockchain architect است: قراردادها برای کدام شبکه نوشته شده‌اند؟ سپیدنامه از ZK-Rollup صحبت می‌کند — اما کدام chain مشخص؟ آیا deployment script وجود دارد؟ آیا constructor arguments هر قرارداد مستند شده‌اند؟ آیا حتی یک قرارداد روی testnet deploy و تست شده؟

## آنچه در این سند جایی ندارد

موارد زیر در **سند بازبینی امنیتی** پوشش داده شده‌اند و نباید در اینجا تکرار شوند:

- مسیرهای حمله و threat modeling
- سوءاستفاده از `CRAWLER_ROLE`
- سطح حمله ZK proof
- راستی‌آزمایی رسمی
- سناریوهای exploit
- replay attacks به عنوان تهدید امنیتی

---

## چه نوع بازخوردی مورد نیاز است

Iran-OS به موارد زیر نیاز دارد — نه تأیید:

- **بازبینی یکپارچه‌سازی:** آیا قراردادها به‌درستی با هم کار می‌کنند؟
- **بازبینی ترتیب استقرار:** آیا deployment sequence ایمن و مستند است؟
- **نقد معماری:** آیا تفکیک مسئولیت‌ها منطقی است؟
- **نقد قابلیت نگهداری:** آیا این سیستم در درازمدت قابل نگهداری است؟
- **بازبینی سیم‌کشی اوراکل:** آیا data pipeline از اوراکل تا Kernel درست است؟
- **بازبینی مدل state:** آیا state machines قراردادها کامل و بدون حالت undefined هستند؟
- **بازبینی رویداد و indexing:** آیا داده کافی برای سیستم‌های خارجی emit می‌شود؟
- **بازبینی نام‌گذاری و ساختار فایل:** آیا سازمان‌دهی مخزن با معماری همخوانی دارد؟
- **بازبینی ابزار استقرار:** کدام ابزار، کدام شبکه، کدام پیکربندی؟

## Iran-OS به دنبال تأیید مهندسی از طریق خوش‌بینی نیست

این پروژه از طریق فرض صحت پیشرفت نمی‌کند. معماری قوی‌تر از طریق بازبینی، نقد، integration testing و شواهد شکل می‌گیرد.

یک ایراد معماری شناسایی‌شده توسط یک مهندس مستقل، ارزشی بیش از هر تأییدی دارد.

اگر طراحی‌ای نادرست است، باید پیش از استقرار اصلاح شود.
