# Reserve Integrity Invariant Matrix — Architecture Formalization (Step-49)

## Scope and Non-Goals

This document is a **documentation-only** formalization of a single, consolidated **invariant matrix** for IranOS, drawn entirely from Steps 41–48. It restates — in compact, auditable, cross-referenced form — the load-bearing invariants that protect reserve integrity, treasury accounting integrity, classification integrity, SWF integrity, monetary expansion integrity, allocation/disbursement integrity, and freeze/reclaim integrity.

This document does not change, and must not be read as changing:

- Any Solidity contract, interface, storage layout, or event.
- Any threshold, multi-sig requirement, or timeout constant.
- Any role, modifier, or access-control assumption.
- The constitutional doctrine values `MIN_RESERVE_RATIO = 333` (33.3%, in thousandths) and `LIQUIDITY_CAP = 900,000,000,000 × 1e18` (`MAX_SUPPLY` in `PahlaviToken.sol`, `LIQUIDITY_CAP` in `kernel.sol`).

It introduces **no new authorities, no new roles, and no new trigger codes**. Every invariant listed below is a restatement — not a redefinition — of a rule already established in one of Steps 41–48 or directly traceable to an existing, unmodified contract entry point.

This document is a **synthesis and direct extension** of, and is subordinate to, the full Step-41–48 series:

- [SOVEREIGN_RESERVE_MODEL.md](SOVEREIGN_RESERVE_MODEL.md) (Step-41) — reserve, treasury, SWF classes and eligibility.
- [TREASURY_ACCOUNTING_RULES.md](TREASURY_ACCOUNTING_RULES.md) (Step-42) — accounting boundaries, recognition rules, prohibited treatments, separation principle.
- [LAYER_INTERACTION_MODEL.md](LAYER_INTERACTION_MODEL.md) (Step-43) — authority, data-flow, accounting-flow, trigger-flow, freeze-routing boundaries.
- [RESERVE_CLASSIFICATION_PROTOCOL.md](RESERVE_CLASSIFICATION_PROTOCOL.md) (Step-44) — classification states, lifecycle transitions, eligibility tests, declassification, double-counting prevention.
- [MONETARY_EXPANSION_CONSTRAINTS.md](MONETARY_EXPANSION_CONSTRAINTS.md) (Step-45) — expansion eligibility, prohibited expansion paths, ratio/cap protection, breach conditions.
- [WEALTH_FUND_STATE_TRANSITIONS.md](WEALTH_FUND_STATE_TRANSITIONS.md) (Step-46) — SWF lifecycle states, allowed/prohibited transitions, no-new-authorities.
- [SOVEREIGN_TREASURY_FLOW_MODEL.md](SOVEREIGN_TREASURY_FLOW_MODEL.md) (Step-47) — end-to-end value-flow paths, reserve-entry/exit, freeze-and-reclaim routing, citizen welfare funding boundaries, prohibited flow paths.

This document **adds no new rule**. Its sole contribution is to collect the invariants already scattered across Steps 41–48 into a single matrix — indexed by ID, stated as a rule, mapped to the domain it protects, paired with the condition that would constitute its violation, and traced to the document where it was first formalized. Where this matrix and any prior document appear to differ in wording or emphasis, the prior document (and, beneath it, the underlying contracts and protocols) remains authoritative — this matrix is an index, not a redefinition.

## How to Read This Matrix

- **Invariant ID**: a stable identifier of the form `<DOMAIN>-<NN>`, used for cross-referencing in audits, test design, and future formal-verification work. IDs are matrix-local — they do not correspond to, replace, or alias any contract constant, event name, or trigger code.
- **Rule**: the invariant stated as a property that must always hold.
- **Protected Domain**: the accounting/governance domain whose integrity the invariant safeguards.
- **Violation Condition**: the concrete state or action that would constitute a breach of the rule — i.e., what an audit, test suite, or monitoring process should treat as a finding.
- **Authoritative Source Document**: the Step-41–48 document (and, transitively, the contract or protocol beneath it) where the invariant was first formalized. That document — and the contract/protocol beneath it — remains authoritative; this matrix is a navigational index.

## Summary

This document consolidates the load-bearing invariants formalized across Steps 41–48 into a single Reserve Integrity Invariant Matrix spanning seven domains: Reserve Integrity (5 invariants — classification correctness, doctrine-bound recognition, single entry/exit paths, deliberate action, and boundary symmetry), Treasury Accounting Integrity (5 — no netting/merging, single custodial record, custody/classification separation, auditability/reconciliation, exact-once accounting), Classification Integrity (5 — exactly-one-state, prohibited-path exclusion, sovereignty of action, non-borrowing, binary eligibility), SWF Integrity (5 — state consistency, fixed-formula intra-layer flow, withdrawal authorization, reclaim-credit accounting-only treatment, no new authorities), Monetary Expansion Integrity (6 — eligibility conjunction, liquidity-cap absoluteness, instantaneous reserve-ratio evaluation, non-self-referential backing, trigger-source integrity, breach-response routing), Allocation/Disbursement Integrity (6 — lifecycle sequencing, source eligibility, SWF spending-path exclusivity, provincial fixed-formula allocation, spend/classification reconciliation, input integrity), and Freeze/Reclaim Integrity (5 — frozen-asset exclusion, freeze lifecycle integrity, routing exclusivity, reclaim/classification separation, routing-actor exclusivity) — 37 invariants in total, each traced to its authoritative Step-41–48 source and, beneath that, to the underlying contracts and protocols.
