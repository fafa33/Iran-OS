# Runtime Enforcement Mapping — Architecture Formalization (Step-50)

## Scope and Non-Goals

This document is a **documentation-only** formalization that maps each invariant defined in [RESERVE_INTEGRITY_INVARIANT_MATRIX.md](RESERVE_INTEGRITY_INVARIANT_MATRIX.md) (Step-49) to its actual runtime enforcement surface — the contract(s), function(s), enforcement mechanism, and test coverage that realize (or fail to realize) it on-chain today.

This document does not change, and must not be read as changing:

- Any Solidity contract, interface, storage layout, or event.
- Any threshold, multi-sig requirement, or timeout constant.
- Any role, modifier, or access-control assumption.
- Any test file or test assertion.
- The constitutional doctrine values `MIN_RESERVE_RATIO = 333` (33.3%, in thousandths) and `LIQUIDITY_CAP = 900,000,000,000 × 1e18` (`MAX_SUPPLY` in `PahlaviToken.sol`, `LIQUIDITY_CAP` in `kernel.sol`).

It introduces **no new doctrine, no new roles, no new authorities, no new thresholds, no new trigger codes, no new storage, no new contracts, and no new timeouts**. Every mapping below points only to contract functions, test files, and architecture documents that already exist, unmodified.

This document is a **direct extension** of, and is subordinate to, the full Step-41–49 series — most directly:

- [RESERVE_INTEGRITY_INVARIANT_MATRIX.md](RESERVE_INTEGRITY_INVARIANT_MATRIX.md) (Step-49) — the invariant matrix this document maps to runtime enforcement, invariant-by-invariant.
- [SOVEREIGN_RESERVE_MODEL.md](SOVEREIGN_RESERVE_MODEL.md) (Step-41), [TREASURY_ACCOUNTING_RULES.md](TREASURY_ACCOUNTING_RULES.md) (Step-42), [LAYER_INTERACTION_MODEL.md](LAYER_INTERACTION_MODEL.md) (Step-43), [RESERVE_CLASSIFICATION_PROTOCOL.md](RESERVE_CLASSIFICATION_PROTOCOL.md) (Step-44), [MONETARY_EXPANSION_CONSTRAINTS.md](MONETARY_EXPANSION_CONSTRAINTS.md) (Step-45), [WEALTH_FUND_STATE_TRANSITIONS.md](WEALTH_FUND_STATE_TRANSITIONS.md) (Step-46), [SOVEREIGN_TREASURY_FLOW_MODEL.md](SOVEREIGN_TREASURY_FLOW_MODEL.md) (Step-47), [TREASURY_ALLOCATION_DISBURSEMENT_MODEL.md](TREASURY_ALLOCATION_DISBURSEMENT_MODEL.md) (Step-48) — the documents in which each mapped invariant was originally formalized.

This document **adds no new rule and proposes no new enforcement mechanism**. Where an invariant currently has no contract-level or test-level enforcement, this document records that fact plainly — it does not propose code, tests, or contracts to close the gap. Identifying an invariant as "documentation-only" is itself the architecture-level finding; closing such a gap, if ever undertaken, is a separate, explicitly-scoped engineering effort outside this document's scope.

## How to Read This Mapping

For each invariant defined in [RESERVE_INTEGRITY_INVARIANT_MATRIX.md](RESERVE_INTEGRITY_INVARIANT_MATRIX.md) (Step-49), this document records:

- **Enforcing Contract**: the Solidity contract whose code realizes (in whole, in part, or not at all) the invariant's rule at runtime. "— (none)" indicates no contract currently enforces the rule directly.
- **Enforcing Function(s)**: the specific function(s), modifier(s), or `require`/`revert` conditions that carry out the enforcement.
- **Enforcement Type**: one of the six categories below — restated from the task requirements, used consistently across the mapping:
  - **Role gate**: an `AccessControl` role check (`onlyRole`, `onlyKernel`, `onlyCouncil`, etc.) restricting who may call a function.
  - **State machine**: an enum/status field and the `require`/transition logic that constrains valid state-to-state movement (e.g., `FreezeStatus`, `Transaction.executed`).
  - **Invariant check**: an arithmetic or compositional `require` that must hold at the moment of execution (e.g., `reserveCompliant`, balance-sufficiency checks).
  - **Accounting rule**: a ledger-update pattern that guarantees conservation, single-crediting, or exact-once effects (e.g., debit/credit pairs, `executed` flags, `totalDeposited`/`totalWithdrawn`).
  - **Threshold rule**: a fixed numeric constant or formula gating an action (e.g., `MULTISIG_REQUIRED = 3`, `PROVINCIAL_SHARE = 300`, `ANNUAL_YIELD = 150`, `productivityScore > 70`).
  - **Lifecycle rule**: a multi-step, multi-call sequence that must complete in order for an effect to occur (e.g., `proposeWithdrawal` → `signWithdrawal` → execution; `Active` → `UnderReview` → `Confirmed` → routing).
- **Related Test File(s)**: existing test file(s) under `test/` whose assertions exercise the enforcement (where any exist).
- **Related Document(s)**: the Step-41–49 document(s) where the invariant and its rationale were formalized.
- **Enforcement Classification**: one of **Contract-Enforced**, **Test-Enforced**, **Documentation-Only**, or **Mixed** (defined precisely in the "Enforcement Classification Legend" section below), stated explicitly for every invariant.

A mapping entry of "— (none)" in any column is itself a finding, not an omission — it records, at the architecture level, that the corresponding enforcement surface does not currently exist. This document neither fabricates such a surface nor recommends one; it records what is, so that future audit, test-design, or engineering work can address gaps deliberately and explicitly.

## Enforcement Classification Legend

- **Contract-Enforced**: the invariant's rule is actively checked and would cause a reverting transaction (or a structurally-impossible state) if violated, by code that already exists, unmodified, in a deployed contract — independent of whether a test currently exercises it.
- **Test-Enforced**: the invariant's rule is not independently guaranteed by contract code alone (e.g., it depends on off-chain process discipline, governance behavior, or composition of multiple contract calls), but an existing test file asserts the expected behavior and would fail if the rule were violated in the tested scenarios.
- **Documentation-Only**: the invariant's rule exists solely as an architecture-level statement in Steps 41–49 — no contract function checks it at runtime, and no existing test file asserts it, because the underlying on-chain concept (e.g., "Sovereign Reserve State classification" as a discrete, queryable status) does not exist as a first-class contract construct.
- **Mixed**: part of the invariant's rule is actively enforced by contract code (and possibly tested), while another part of the same rule rests on documentation-level discipline that no contract or test currently checks. The mapping entry specifies which part is which.

## Enforcement Classification Summary

This section, as required, explicitly identifies which invariants fall into each of the four enforcement classifications. (Several invariants are **Mixed** and therefore appear in more than one summary where the table above splits their rule into separately-classifiable parts; the canonical classification for each ID is the one stated in its row above.)

### Contract-Enforced (and, where noted, also independently Test-Enforced)

`TAI-05`, `SWF-01`, `SWF-02`, `SWF-03`, `MEX-01`, `MEX-02`, `MEX-03`, `ALD-03`, `ALD-04`, `FRC-02`, `FRC-03`, `FRC-05`

These invariants are actively checked by `require`/modifier logic in deployed, unmodified contract code (`SovereignWealthFund.sol`, `PahlaviToken.sol`, `Provincial.sol`, `AssetFreeze.sol`, `kernel.sol`) such that a violating transaction would revert or a violating state would be structurally unreachable — and each is independently exercised by an existing test file.

### Test-Enforced (asserted by tests, not independently guaranteed by contract structure alone)

No invariant in this matrix falls into this category in pure form — every rule that has meaningful test coverage in this codebase is backed by a corresponding on-chain check (and is therefore classified as Contract-Enforced-and-Test-Enforced, or Mixed where only part of the rule is checked on-chain). This is itself a notable finding: the existing test suite verifies contract behavior rather than substituting for it — there is no invariant whose sole guarantee is "the test currently passes."

### Documentation-Only (no contract check, no test assertion — exists solely as an architecture-level standard)

`RES-01`, `RES-03`, `RES-05`, `TAI-03`, `CLS-01`, `CLS-04`, `MEX-04`, `ALD-05`

These invariants describe properties of constructs — most centrally, "reserve classification" as a discrete, queryable, on-chain action or state — that do not exist as first-class elements of the deployed contracts. They are governance, audit, and review standards formalized in Steps 44, 45, 47, and 48, and they remain exactly that: standards for human and process discipline, not runtime-checked guarantees. This document records this honestly rather than implying a contract-level guarantee that does not exist.

### Mixed (part contract/test-enforced, part documentation-only — see individual rows for the precise split)

`RES-02`, `RES-04`, `TAI-01`, `TAI-02`, `TAI-04`, `CLS-02`, `CLS-03`, `CLS-05`, `SWF-04`, `SWF-05`, `MEX-05`, `MEX-06`, `ALD-01`, `ALD-02`, `ALD-06`, `FRC-01`, `FRC-04`

For each of these, the table above identifies precisely which portion of the rule is realized by existing contract code (and tested), and which portion rests on documentation-level discipline with no corresponding on-chain check. The most common pattern is: the contract enforces a *concrete, adjacent mechanism* (a role gate, a fixed formula, a state enum) that *substantially supports* the invariant, while a *compositional or intentional* element of the same invariant (e.g., "the figure must be composed only of eligible value," "the decision must not have been justified by X") cannot be checked on-chain because it depends on facts (origin, intent, composition history) that the contract does not — and structurally cannot — represent.

## Cross-Cutting Observation: Why "Classification" Is the Central Gap

A pattern recurs across nearly every **Documentation-Only** and **Mixed** entry above: the architecture-level concept of **"Sovereign Reserve State classification"** (formalized in [RESERVE_CLASSIFICATION_PROTOCOL.md](RESERVE_CLASSIFICATION_PROTOCOL.md), Step-44, and used pervasively in Steps 45–49) has **no on-chain representation**. There is no contract enum, status field, mapping, or function that records whether a given balance "is" Sovereign Reserve, Non-Reserve Treasury, Pending Classification, or any of the other six states — these are architecture-documentation labels applied, by governance convention, to balances that otherwise live in ordinary Treasury or SWF storage.

This is **not** a defect this document proposes to fix — doing so would be a contract change, squarely outside this document's documentation-only scope, and outside the scope of a Step-50 mapping exercise. It is, however, the single most important fact this mapping surfaces: a meaningful fraction of the invariant matrix's most doctrine-critical guarantees (the eight Eligibility Tests, the single entry/exit path, the prohibition on auto-classification of reclaimed or deposited value, the symmetry of entry/exit rigor, the requirement to re-examine classification on exit) are, today, **enforced entirely through governance discipline and architecture-document review** — not through any reverting `require` statement or any assertion in the existing test suite. Steps 41–49 already say as much in places (e.g., Step-44's own note that "this document does not define an automated blocking mechanism (none exists in the contracts)"); this document's contribution is to make that fact systematically visible, invariant-by-invariant, in one place.

## Summary

This document maps every invariant in the Step-49 [Reserve Integrity Invariant Matrix](RESERVE_INTEGRITY_INVARIANT_MATRIX.md) — across all seven families (RES-*, TAI-*, CLS-*, SWF-*, MEX-*, ALD-*, FRC-*) — to its actual runtime enforcement surface: the enforcing contract, the enforcing function(s), the enforcement type (role gate / state machine / invariant check / accounting rule / threshold rule / lifecycle rule), the related existing test file(s), and the related Step-41–49 document(s). It explicitly classifies each of the 37 invariants as **Contract-Enforced** (12 invariants — fully realized and tested by existing, unmodified contract code), **Test-Enforced in pure form** (none — every meaningfully-tested rule in this codebase is backed by an on-chain check), **Documentation-Only** (8 invariants — existing solely as architecture-level governance/audit standards, most centrally because "Sovereign Reserve State classification" has no on-chain representation), and **Mixed** (17 invariants — partially realized by concrete contract mechanisms, partially resting on documentation-level discipline for compositional or intentional properties the contracts cannot represent). It surfaces, as a cross-cutting observation, that the absence of an on-chain classification construct is the single recurring root cause behind nearly every Documentation-Only and Mixed finding — a fact already implicit in Steps 41–49 individually, made systematically visible here for the first time. It proposes no new contract, test, role, threshold, trigger code, or doctrine value to close any gap; it records, faithfully and traceably, what is enforced where today. It explicitly preserves `MIN_RESERVE_RATIO = 333`, `LIQUIDITY_CAP = 900,000,000,000 × 1e18`, the non-sovereignty of oracle signals, the non-automatic backing status of reclaimed assets, the exclusion of frozen assets from reserve recognition, and the structural separation of welfare/wage obligations from reserve accounting. It is a reference specification intended to directly support future audits, invariant-based test design, and formal-verification scoping, consistent with the documentation-only formalizations already present under `docs/`.
