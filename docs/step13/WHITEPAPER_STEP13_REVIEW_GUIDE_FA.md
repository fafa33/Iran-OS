# راهنمای فارسی بازبینی و ثبت نظر درباره نگاشت سپیدنامه به سیستم

**نام فنی:** Step 13 Review Guide  
**نوع سند:** راهنمای عمومی و فارسی‌محور برای فهم، بازبینی و ثبت نظر  
**وضعیت:** باز؛ این سند گام ۱۲ یا گام ۱۳ را نمی‌بندد.

## ۱. این سند برای چیست؟

این راهنما برای این ساخته شده که مشارکت‌کننده فارسی‌زبان، بازبین، متخصص یا خواننده عمومی بداند گام ۱۳ چیست و چطور می‌تواند درباره نگاشت سپیدنامه به سیستم نظر بدهد.

گام ۱۳ یعنی تلاش برای روشن‌کردن این مسیر:

سپیدنامه → اصل یا بند → بخش فنی یا حکمرانی → وضعیت اجرا → شواهد، تست، issue یا signoff لازم

به زبان ساده‌تر: هر حرف مهم در سپیدنامه باید معلوم باشد در کجای پروژه دیده شده، کجا هنوز باز است، و برای بررسی بیشتر به چه چیزی نیاز دارد.

## ۲. این سند چه چیزی نیست؟

این سند اعلام نمی‌کند که پروژه آماده اجراست.  
این سند اعلام نمی‌کند که audit کامل شده است.  
این سند اعلام نمی‌کند که formal verification کامل شده است.  
این سند هیچ blockerای را نمی‌بندد.  
این سند هیچ evidenceای را پذیرفته‌شده اعلام نمی‌کند.  
این سند هیچ signoff رسمی ایجاد نمی‌کند.

گام ۱۲ همچنان باز است.  
گام ۱۳ همچنان باز است.

## ۳. چه کسانی می‌توانند نظر بدهند؟

افراد مختلف می‌توانند از زاویه‌های متفاوت کمک کنند:

| نوع مشارکت‌کننده | چه چیزی را بررسی می‌کند؟ |
| --- | --- |
| خواننده عمومی فارسی‌زبان | آیا متن قابل فهم است؟ آیا باعث سوءبرداشت می‌شود؟ |
| بازبین منشور و سپیدنامه | آیا معنی اصلی سپیدنامه حفظ شده است؟ |
| بازبین حکمرانی | آیا نقش‌ها، اختیارها و مسئولیت‌ها درست تفکیک شده‌اند؟ |
| بازبین حقوقی | آیا متن ادعای حقوقی یا اجرایی زودرس ایجاد نمی‌کند؟ |
| بازبین اقتصادی | آیا ادعای اقتصادی از وضعیت واقعی evidence جدا شده است؟ |
| بازبین فنی | آیا نگاشت به repo، test، contract یا issue درست است؟ |
| بازبین audit یا formal verification | آیا چیزی به‌اشتباه audit complete یا proof complete جلوه داده نشده است؟ |

## ۴. نظر خوب چه ویژگی‌هایی دارد؟

نظر خوب باید روشن، محدود و قابل بررسی باشد.

برای هر نظر بهتر است این موارد مشخص شود:

| مورد | توضیح |
| --- | --- |
| بخش مورد نظر | کدام workstream، سند یا بند؟ |
| نوع نظر | ابهام، خطای مفهومی، شکاف اجرایی، نیاز به evidence، نیاز به signoff یا پیشنهاد ویرایشی |
| دلیل | چرا این بخش نیاز به اصلاح یا بررسی دارد؟ |
| issue مرتبط | اگر موضوع به evidence یا signoff مربوط است، به issueهای #12 تا #19 وصل شود. |
| claim check | آیا این نظر ممکن است ناخواسته ادعای آمادگی تولید، audit، formal verification، signoff یا بسته‌شدن blocker ایجاد کند؟ |

## ۵. تفاوت نظر عمومی با signoff رسمی

نظر عمومی ارزشمند است، اما signoff رسمی نیست.

یعنی اگر کسی از پروژه حمایت کند، متن را تأیید کند، یا پیشنهاد بدهد، این به معنی بسته‌شدن blocker، پذیرفته‌شدن evidence یا تأیید انتشار نیست.

برای signoff رسمی، باید evidence و نقش بازبین مشخص باشد و مسیر مربوط از issueهای گام ۱۲ عبور کند.

## ۶. مسیر ثبت نظر

برای ثبت نظر، بهتر است یکی از این مسیرها استفاده شود:

- اگر نظر درباره فهم عمومی یا خوانایی است: در issue یا PR کوچک مستنداتی ثبت شود.
- اگر نظر درباره evidence یا signoff است: به issueهای #12 تا #19 وصل شود.
- اگر نظر درباره یکی از workstreamهای گام ۱۳ است: نام همان workstream و فایل مربوط ذکر شود.
- اگر نظر فقط ویرایشی است: باید روشن شود که معنی سیاسی، حقوقی، فنی یا حکمرانی متن را تغییر نمی‌دهد.

## ۸. خط قرمزهای بازبینی

در هیچ نظر، issue، PR یا سند تکمیلی نباید بدون evidence و signoff معتبر ادعا شود:

- پروژه آماده اجراست.
- انتشار تأیید شده است.
- audit بیرونی کامل شده است.
- formal verification کامل شده است.
- blocker بسته شده است.
- evidence پذیرفته شده است.
- reviewer signoff دریافت شده است.
